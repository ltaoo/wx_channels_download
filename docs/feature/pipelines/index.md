# 自动化流程示例

这三个 JSON 使用当前项目的流程定义格式，默认面向微信视频号。打开下方示例页面，点击 JSON 代码块右上角的复制按钮，即可在「自动化 → 导入 Pipeline」中粘贴导入。

| 示例 | 功能 | 建议 Cron |
| --- | --- | --- |
| [创作者视频同步](./creator-video-sync.md) | 逐页检查已有下载任务，仅下载缺失视频，遇到整页已存在时停止 | `0 12,18 * * *`，每天 12:00、18:00（已内置） |
| [创作者直播录制](./creator-live-record.md) | 查询当前直播，正在直播时创建录制任务，未开播正常结束 | `*/1 * * * *`，每分钟 |
| [创作者新视频通知](./creator-new-video-notify.md) | 按本地下载任务判断新视频，支持企业微信和通用 Webhook | `*/5 * * * *`，每五分钟 |

## 导入和配置

1. 选择需要的流程，复制并导入该页面的完整 JSON。每次导入会生成新的 Pipeline ID。
2. 第一、三个流程在「校验创作者参数」节点声明了必填字符串配置 `username` 和可选「备注」。导入后在 `/automation` 点击对应流程的「配置」，填写实际创作者，例如 `xxx@finder`，保存后手动和定时运行共用，无需再传运行参数；自动清除 `wxchannels:` 前缀和首尾空白。第二个流程仍在「配置」节点中修改 `creator_username`。username 不是昵称，可以从账号搜索结果取得。
3. 前两个流程的 `download_dir` 留空时使用应用默认下载目录，也可以填写下载器所在机器的绝对路径。
4. 第一个流程通过顶层 `triggers` 内置了已启用的定时触发器，导入时自动创建并关联开始节点；第二、三个流程需在开始节点添加定时触发器，填写上表 Cron，保存 Pipeline。Cron 使用下载器进程的时区，调度器约每 30 秒检查一次。
5. 保持下载器运行以及视频号查询能力可用。首次运行可从定时规则的立即执行入口进行手动验证。

Cron 是描述定时执行规则的表达式，本项目使用 5 段格式：`分 时 日 月 星期`。`0 12,18 * * *` 表示每天的 12 点和 18 点，在第 0 分钟触发；逗号表示多个值，星号表示任意值。

第一个流程将「获取创作者视频列表」封装为独立子流程，传入 `username`、`next_marker`、接口地址、请求方法和认证配置，返回 HTTP 接口响应。默认 GET 请求 `http://127.0.0.1:2022/api/channels/contact/feed/list`，可在流程的「配置」中填写 `url`、选择 `method` 和填写可选 `token`；method 留空使用 GET。username 和 next_marker 放在查询参数中，POST 等带请求体的方法还会发送同名 JSON 字段，GET/HEAD 不发送请求体。token 使用 secret 输入遮罩，通过 Bearer 认证发送，留空不发送认证头。列表可使用下载器的包装结构，也可直接返回 `BaseResponse/object` 原始结构；同时兼容驼峰和下划线命名的分页、视频字段。`next_marker` 为空表示从头获取，后续调用使用响应中的 `lastBuffer` 或 `last_buffer`；没有单独的「获取第一页」操作。

主流程回连到同一个分页子流程调用节点实现 loop。每次调用使用独立作用域，并行执行「提交上一页筛选出的缺失视频下载任务」与「按当前 next_marker 调用获取列表子流程」。首次调用待下载列表为空；末页检查完成后，最后调用仅提交剩余下载任务，不再请求列表。两条分支完成并汇合后，主流程收集本页视频的 `wxchannels:<视频 ID>`，通过一次 `check_download_task_contents` 服务调用批量查询是否已有下载任务。整页检查完成后汇总结果，全部已存在则终止，否则保存缺失视频和下一页游标，再次调用同一个分页子流程。

JSON 使用循环连线复用同一调用节点，不使用引擎禁止的递归 `flow_id` 引用。各层子流程都包含节点坐标，可以随 JSON 一并导入，无需单独创建依赖流程。下载分支返回表示任务已提交，不等待文件下载完成。空页或仅包含非视频内容的页不会被当作「整页已存在」，有下一页时会继续翻页；没有下一页时正常结束。通知流程同样逐页检查本地下载任务，遇到整页已存在停止；直播流程使用 JS、设置变量和条件分支回连遍历分页。

视频同步的下载分支使用列表中的完整视频对象调用 `create_download_task`，不会额外查询视频详情，也不要求本机视频号页面保持 socket 连接。自定义列表接口必须返回媒体 URL、URL token 和加密视频所需的解密 key；仅提供视频 ID 无法创建完整下载任务。

`max_pages` 默认 1000，`max_videos` 默认 100000；超过限制会明确失败。循环与子流程共用引擎步骤预算，达到执行步骤上限也会失败。

## 新视频通知的额外配置

通知示例按「准备参数 → 分页扫描与存在性检查 → 推送消息」从左到右排列，分页循环和通知循环分别放在下方。

新视频判断与 `01_creator_video_sync.json` 相同：逐页获取创作者视频，每页通过一次 `check_download_task_contents` 调用，按 `wxchannels:<视频 ID>` 批量查询本地下载任务。没有任务的视频加入本次待通知列表；整页视频都有任务时立即停止翻页。空页或仅包含非视频内容的页不会被当作「整页已存在」。批量结果按 ID 对照校验，缺项、重复项或任务数与存在性不一致都会失败；先完成扫描和检查，再逐条推送，本次扫描内同一视频只通知一次。

1. 导入后在 `/automation` 点击该流程的「配置」，在「校验创作者参数」填写 `username` 和可选备注。
2. 在「配置消息推送」中填写下表各项并保存。推送方式用下拉选择，消息模板用多行输入，token 使用密码框。
3. 可直接手动触发验证；要自动监控，在开始节点添加定时触发器，建议 Cron 为 `*/5 * * * *`。

此示例不再要求定时规则 ID 或本机 API 地址，也不使用首次运行基线或 `creator_video_monitor`。第一次运行就会通知扫描范围内没有下载任务的视频。

| 配置项 | 必填 | 用途 |
| --- | --- | --- |
| 消息推送方式 `push_method` | 是 | 企业微信机器人（`wecom`）或通用 HTTP Webhook（`webhook`） |
| 接口地址 `push_url` | 是 | 完整 HTTP(S) 推送接口地址 |
| token `push_token` | 否 | 企业微信机器人 key，或通用 Webhook 的 Bearer token |
| 消息模板 `message_template` | 否 | 留空使用内置新视频通知；可换行 |

企业微信接口地址可填写 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send`，再在 token 中填写机器人 key。也支持完整的带 `?key=...` 地址，此时 token 可以留空；填写 token 会替换地址中的 key。企业微信推送使用文本消息，收到 HTTP 2xx 且响应 `errcode: 0` 才确认发送成功。

通用 Webhook 通过 POST 发送 JSON；填写 token 时添加 `Authorization: Bearer <token>`，留空时不加认证。接口收到的结构如下：

```json
{
  "content": "根据消息模板生成的文本",
  "username": "creator@finder",
  "remark": "创作者备注",
  "video_id": "123",
  "title": "新视频标题",
  "published_at": 1700000000
}
```

通用 Webhook 需要返回 HTTP 2xx。如果 JSON 响应包含 `success: false`、`ok: false`、非零且非 200 的 `code` 或非零的 `errcode`，仍视为推送失败，保留视频待下次重试。

消息模板支持 `{username}`、`{remark}`、`{title}`、`{video_id}`、`{published_at}`，例如：

```text
{remark} 发布了新视频
账号：{username}
标题：{title}
视频 ID：{video_id}
发布时间：{published_at}
```

未知模板占位符会在扫描和推送前报错。模板只做文本替换，不执行其中的代码。`published_at` 使用平台返回的原始发布时间。

通知流程只发送消息，不创建下载任务，也不另外保存「已通知」清单。已通知但仍没有下载任务的视频，在下次运行中仍会被视为新视频，可能再次通知；需要避免此类提醒时，可配合下载/同步流程创建任务。

## 运行结果与边界

- 列表仅包含平台接口当前允许访问的视频，不包含隐藏、已删除或无权限内容。需要继续翻页时，分页游标缺失或重复会明确失败；平台响应异常也会失败；通知流程不会在扫描或存在性检查失败时发送部分结果。
- 视频同步采用增量规则，遇到整页已存在即停止，不保证补齐更旧页面的下载缺漏。「已存在」指已有下载任务，包含未完成或失败的任务，并非确认本地文件已完整下载；失败任务需要在下载任务中重试。`existing_action: "skip"` 还会在检查后任务被其他运行抢先创建时跳过重复下载。
- `sync_summary.stop_reason` 为 `all_existing` 或 `no_more_pages`；`checked` 和 `skipped` 按各页检查次数累计，跨页重复视频可能重复计数，`videos` 为本次扫描发现的不同视频数。`submitted` 不表示文件已经下载完成，实际文件结果在下载任务页面查看。
- 直播录制使用原生直播下载工具，以相同直播任务的 `skip` 策略避免每次轮询重复录制。它不等待直播结束；录制中断后的恢复仍需处理下载任务。平台在检查后刚好结束直播时，本次启动可能失败，下一次仍会重新检查。
- 通知按视频 ID 对应的本地下载任务判断新增，而非按标题、发布时间或首次扫描时间。遇到整页已存在即停止，因此不会继续检查更旧页面上的缺失视频。
- 推送失败会停止本次运行；下次重新按下载任务检查。发送请求超时但实际已送达时，也可能再次提醒。本流程未使用推送端的幂等确认接口。
- 修改 username、消息推送方式、接口地址、token 或模板后先保存。下载任务查询失败或响应不完整会使通知流程失败，不会把未知状态当作新视频。

## 批量下载任务存在性查询

HTTP：`POST /api/v1/download_task/check_contents`。自动化 ServiceNode / MCP 工具：`check_download_task_contents`。两者使用同一批量查询服务。

请求：

```json
{"content_ids":["wxchannels:123","wxchannels:456"]}
```

HTTP 响应的 `data`（也是 ServiceNode 的输出）：

```json
{
  "list": [
    {"content_id":"wxchannels:123","exists":true,"task_count":2},
    {"content_id":"wxchannels:456","exists":false,"task_count":0}
  ],
  "total": 2
}
```

最多接受 10000 个字符串 ID，去掉首尾空白和重复 ID，按首次出现顺序返回，未找到的 ID 也明确返回 `exists: false`。空数组返回空 `list` 和 `total: 0`。所有任务状态都计入存在性，已删除任务排除；查询失败返回错误，不返回部分或伪造的「不存在」结果。数据库按最多 500 个 ID 分组执行 `IN` 查询，常规一页只需一次查询。

更新服务并重新导入示例后使用批量节点；已经导入的旧流程不会随示例文件自动更新。

## 非浏览器验证

在项目根目录运行：

```sh
go test ./internal/services -run TestImportCreatorVideoSyncSchedule
npm --prefix docs run build
```

Go 测试验证视频同步示例的真实导入、节点配置声明和定时触发规则；文档构建检查页面链接与 JSON 引用。浏览器中的复制和导入行为由用户手动验证。
