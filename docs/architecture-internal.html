关键约束 · Invariants

01 注册即声明

tool 定义与 handler 同文件、同一次声明（tool_declarations）。不存在「已定义未接线」的 tool。

可用性由 supports 谓词在注册期求值，后端缺失 → tool 从 tools/list 中消失，而非运行时抛错。

02 服务层几乎不感知 MCP

业务服务不 import internal/mcpserver；方向是 mcpserver → application/mcp_backends → services。仅两处例外： mcp.go（MCPService 本身就是 MCP 传输）与 user_flow.go（自动化编辑器要枚举工具定义）。

Bridge 不在例外之列 —— 它直连自有的 bridge_wxchannels_adapter / bridge_wxmp_adapter，不再借 mcpserver 的 capability 做参数校验。

03 一套注册表，两种传输

Streamable HTTP、stdio remote、以及自动化流程节点共用 ToolSet 与 ExecuteTool，行为一致。

差异只在后端注入：HTTP host 注入进程内 adapter 后端（mcp_wxchannels_backend）， stdio 没有进程内 adapter，回退到经 api_client 转发的 api_wxchannels_backend。stdio 不自带 DB / downloader / adapter， 全部调用都打到已运行的 server 上。

04 手工装配

无 wire/DI 生成。application/start.go:Start() 是唯一组合根：DB → services → MCP → APIServer → events 订阅 → adapters → 启动。

05 双向能力通道

同一份 WXChannelsBackend（内嵌 WXChannelsRuntime）/ WXMPRuntime 抽象有两个实现：MCP 的 HTTP host 走进程内 mcp_wxchannels_backend，无 adapter 的 stdio 走 api_wxchannels_backend（HTTP 转发）。Bridge 不参与这层抽象，它断言进程内 adapter 后直接调用。视频号工具已不再经本进程自己的 REST API 自回环 —— 127.0.0.1:2022/api/channels/* 由 WebsocketRoutes 单例服务，而 ChannelsAdapter 包的正是同一对象，那一跳 HTTP 只带来开销与对 api.hostname/api.port 的硬绑定。

Bridge 为出站 WSS，设备无需公网可达；由 bridge.enabled 控制启停。

06 事件驱动的状态面

events.Bus 同步分发：proxy / service / platform 状态 → RuntimeStatusService；task 增删 → broadcaster；automation → WebSocket 推送。

flowengine.RegisterServiceNode(...ExecuteTool) 让自动化工作流节点可直接调 MCP 工具。
