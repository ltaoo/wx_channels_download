# 创作者自动化 Pipeline

这三个 JSON 使用当前项目的流程定义格式，可在「自动化 → 导入 Pipeline」中粘贴文件内容导入。默认面向微信视频号。

| 文件 | 功能 | 建议 Cron |
| --- | --- | --- |
| `01_creator_video_sync.json` | 逐页检查已有下载任务，仅下载缺失视频，遇到整页已存在时停止 | `0 12,18 * * *`，每天 12:00、18:00（已内置） |
| `02_creator_live_record.json` | 查询当前直播，正在直播时创建录制任务，未开播正常结束 | `*/1 * * * *`，每分钟 |
| `03_creator_new_video_notify.json` | 首次扫描建立基线，之后仅通知新增视频，使用企业微信机器人 | `*/5 * * * *`，每五分钟 |

## 导入和配置

1. 分别导入三个 JSON。导入会生成新的 Pipeline ID。
2. 第一个流程声明了必传字符串入参 `username`，导入前将 JSON 顶层 `triggers[0].initial_data.username` 的占位值替换为实际创作者，例如 `xxx@finder`；也可导入后在开始节点的定时触发器执行参数中修改。手动运行时也必须填写 `{"username":"xxx@finder"}`。第二、三个流程仍在「配置」节点中修改 `creator_username`。这里的 username 不是昵称，可以从账号搜索结果取得。
3. 前两个流程的 `download_dir` 留空时使用应用默认下载目录，也可以填写下载器所在机器的绝对路径。
4. 第一个流程通过顶层 `triggers` 内置了已启用的定时触发器，导入时自动创建并关联开始节点；第二、三个流程需在开始节点添加定时触发器，填写上表 Cron，保存 Pipeline。Cron 使用下载器进程的时区，调度器约每 30 秒检查一次。
5. 保持下载器运行以及视频号查询能力可用。首次运行可从定时规则的立即执行入口进行手动验证。

Cron 是描述定时执行规则的表达式，本项目使用 5 段格式：`分 时 日 月 星期`。`0 12,18 * * *` 表示每天的 12 点和 18 点，在第 0 分钟触发；逗号表示多个值，星号表示任意值。

第一个流程将「获取创作者视频列表」封装为独立子流程，入参只有 `username` 和 `next_marker`，返回平台列表响应。`next_marker` 为空表示从头获取，后续调用使用响应中的 `lastBuffer`；没有单独的「获取第一页」操作。

主流程回连到同一个分页子流程调用节点实现 loop。每次调用使用独立作用域，并行执行「提交上一页筛选出的缺失视频下载任务」与「按当前 next_marker 调用获取列表子流程」。首次调用待下载列表为空；末页检查完成后，最后调用仅提交剩余下载任务，不再请求列表。两条分支完成并汇合后，主流程使用 `LoopNode` 对响应中的视频逐条调用 `get_download_tasks`，按 `wxchannels:<视频 ID>` 查询是否已有下载任务。整页检查完成后汇总结果，全部已存在则终止，否则保存缺失视频和下一页游标，再次调用同一个分页子流程。

JSON 使用循环连线复用同一调用节点，不使用引擎禁止的递归 `flow_id` 引用。各层子流程都包含节点坐标，可以随 JSON 一并导入，无需单独创建依赖流程。下载分支返回表示任务已提交，不等待文件下载完成。空页或仅包含非视频内容的页不会被当作「整页已存在」，有下一页时会继续翻页；没有下一页时正常结束。第二、三个流程仍使用 JS、设置变量和条件分支回连遍历分页。

`max_pages` 默认 1000，`max_videos` 默认 100000；超过限制会明确失败。循环与子流程共用引擎步骤预算，达到执行步骤上限也会失败。

## 新视频通知的额外配置

该流程默认对接**企业微信自定义机器人文本 Webhook**。

1. 导入并保存定时触发器后，获取该触发器的 ID（`sched-...`）。可请求 `POST http://127.0.0.1:2022/api/v1/automation/list_schedules`，请求体为 `{"flow_id":"导入后生成的 Pipeline ID"}`，从 `data.list` 取得对应规则的 `id`。
2. 将配置节点的 `monitor_schedule_id` 改为这个 ID。每个监控流程只配置一个定时规则，不要填写另一个 Pipeline 的规则 ID。
3. 将「发送企业微信机器人通知」节点 `config.url` 中的 `REPLACE_WEBHOOK_KEY` 换成自己的机器人 key。
4. 本地状态读取和保存节点默认使用 API 地址 `http://127.0.0.1:2022`。如果应用 API 地址或端口不同，同时修改这两个节点的 URL。2022 是 API 默认端口，2023 是代理端口。
5. 保存流程，先从该定时规则立即执行一次。首次运行只建立基线，不通知历史视频。之后出现新视频时，每条视频发送一条消息。

已知视频 ID 保存在该定时规则的 `initial_data.creator_video_monitor`，重启后保留。更新进度时保留现有参数及 `__automation` 元数据。每条消息成功发送并且企业微信返回 `errcode: 0` 后，才保存该条进度；部分通知失败时，后续运行只补发尚未确认的视频。

删除 `creator_video_monitor` 会在下次运行重新建立基线。更换创作者也会重新建立基线。编辑定时规则参数时，应保留最新的监控进度，避免旧表单覆盖新状态。不要让手动运行和定时运行重叠，或让多个流程共用同一个状态规则；当前接口没有跨运行的状态写入锁。

## 运行结果与边界

- 列表仅包含平台接口当前允许访问的视频，不包含隐藏、已删除或无权限内容。需要继续翻页时，分页游标缺失或重复会明确失败；平台响应异常也会失败，不会用部分结果建立通知基线。
- 视频同步采用增量规则，遇到整页已存在即停止，不保证补齐更旧页面的下载缺漏。「已存在」指已有下载任务，包含未完成或失败的任务，并非确认本地文件已完整下载；失败任务需要在下载任务中重试。`existing_action: "skip"` 还会在检查后任务被其他运行抢先创建时跳过重复下载。
- `sync_summary.stop_reason` 为 `all_existing` 或 `no_more_pages`；`checked` 和 `skipped` 按各页检查次数累计，跨页重复视频可能重复计数，`videos` 为本次扫描发现的不同视频数。`submitted` 不表示文件已经下载完成，实际文件结果在下载任务页面查看。
- 直播录制使用原生直播下载工具，以相同直播任务的 `skip` 策略避免每次轮询重复录制。它不等待直播结束；录制中断后的恢复仍需处理下载任务。平台在检查后刚好结束直播时，本次启动可能失败，下一次仍会重新检查。
- 通知按视频 ID 判断新增，而非按标题或发布时间。首次建基线后，接口后来才变得可见的旧视频也会视为新增。
- 通知采用至少一次语义：发送成功后、进度保存前发生崩溃，或发送请求超时但实际已送达，下一次可能重复发送。企业微信 Webhook 没有本流程可用的幂等确认接口。
- 修改 `creator_username`、通知 URL 等配置后先保存。通知流程的状态进度读取失败或保存失败会使本次运行失败，不会宣称成功。

## 非浏览器验证

在项目根目录运行：

```sh
go test ./examples/pipelines
```

验证使用真实导入、保存、JS、分支、服务节点和 HTTP 节点，替换平台工具与 HTTP 传输返回模拟数据，不连接微信或发送真实通知。浏览器行为由用户导入后手动验证。
